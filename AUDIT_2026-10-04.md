# Auditoria técnica VRTX — 04/10/2026

## Resumo executivo

A branch atual contém uma evolução web significativa: shell próprio, autenticação, onboarding, dashboard, treino, nutrição, progresso, perfil, assinaturas, construtor de treino e uma primeira central de coach.

O principal problema agora não é ausência de infraestrutura: o repositório já contém migrations B2B, RLS, RPCs, Edge Functions de Stripe e APIs Supabase. O problema é **desalinhamento entre o que o web apresenta e o que realmente está conectado**.

Há telas com aparência pronta, mas com ações sem efeito, dados estáticos ou navegação que ainda desemboca em telas mobile. Isso explica por que o preview parece melhor visualmente, mas ainda transmite sensação de produto incompleto.

## Validações realizadas

- `pnpm test:unit`: **14 arquivos, 74 testes aprovados**.
- `pnpm install --frozen-lockfile --offline`: lockfile consistente.
- A branch de redesign contém **41 arquivos alterados**, com cerca de **886 linhas adicionadas** em relação à `main`.
- As migrations Supabase e Edge Functions estão versionadas no repositório.
- Há CI para lint, typecheck, unit e E2E, mas a cobertura atual não valida os fluxos web principais.
- O checkout auditado não apresentou mudanças locais pendentes.

## Achados prioritários

### P0 — corrigir antes de considerar o web pronto para produção

#### 1. A central de coach ainda cai em telas nativas

A rota web `/students` existe, mas estas rotas continuam sem variante web dedicada:

- `app/coach/client/[clientId].tsx`
- `app/coach/adherence/[clientId].tsx`
- `app/coach/measurements/[clientId].tsx`
- `app/coach/nutrition/[clientId].tsx`
- `app/prescribe/[clientId].tsx`

O dashboard web ainda aponta os três atalhos para `/students`, em vez de abrir diretamente prescrição, nutrição, medidas ou aderência. O usuário entra no workspace, mas não consegue executar o fluxo completo de coach dentro da nova experiência.

**Recomendação:** criar um `WebClientWorkspaceScreen` com abas internas:

1. Visão geral;
2. Treinos prescritos;
3. Nutrição;
4. Medidas;
5. Aderência/check-ins;
6. Histórico e observações.

Depois, converter `prescribe`, `adherence`, `measurements` e `nutrition` para wrappers web, mantendo o mobile como fallback.

#### 2. A tela do Coach IA apresenta uma ação sem implementação

Em `src/screens/web/WebSectionScreen.tsx`, a variante `ai` renderiza o botão **Gerar leitura**, mas o handler é `onPress={() => undefined}`. A integração real existe em `src/services/AIInsights.ts` e em `src/screens/AICoachScreen.tsx`, mas não foi conectada à superfície web.

**Recomendação:** extrair a lógica para um componente compartilhado e criar `WebAICoachScreen`, com:

- contexto dos últimos 7 dias;
- estado de carregamento;
- erro/retry;
- resposta estruturada;
- feedback positivo/negativo;
- limite diário e estado Premium;
- histórico de conversa persistido.

#### 3. A área Premium também contém CTA sem ação

A variante `premium` usa `onPress={() => undefined}` para **Conhecer recursos**. O repositório já possui Edge Functions de checkout Stripe e integração de billing, mas o web não fecha o fluxo de conversão.

**Recomendação:** conectar o CTA ao checkout real, tratar loading/erro/retorno e exibir o estado da assinatura a partir de `coach_subscriptions`/perfil. Não deixar o botão parecer interativo se não houver ação.

#### 4. O construtor de treino ainda não está ligado ao modelo completo de templates

`WebWorkoutBuilderScreen` permite editar exercícios, séries, carga e repetições localmente e iniciar uma sessão. Porém, a experiência de produto precisa distinguir claramente:

- criar um treino avulso;
- salvar como template;
- prescrever para um aluno;
- iniciar a sessão agora;
- duplicar um treino anterior.

**Recomendação:** usar os modelos de templates já presentes no mobile e criar um fluxo único de persistência. O botão deve oferecer ações explícitas: **Salvar treino**, **Salvar como modelo**, **Prescrever** e **Começar agora**.

### P1 — alta prioridade de produto e UX

#### 5. Muitas rotas importantes continuam nativas no web

Rotas identificadas como native-only incluem:

- `app/diet/add-meal.tsx`
- `app/diet/goals.tsx`
- `app/templates.tsx`
- `app/measurements.tsx`
- `app/body-composition.tsx`
- `app/gamification.tsx`
- `app/join-coach.tsx`
- `app/history/[id].tsx`
- `app/billing.tsx`
- rotas de detalhes do coach listadas acima.

As telas principais estão bonitas, mas os fluxos de aprofundamento trocam de linguagem visual ao entrar nessas rotas.

**Ordem recomendada:**

1. adicionar refeição e metas;
2. templates e histórico de treino;
3. medidas/composição corporal;
4. client workspace do coach;
5. billing/checkout;
6. gamificação e recursos secundários.

#### 6. Dados estáticos na camada web

Exemplos encontrados em `WebSectionScreen.tsx`:

- água exibida como `0,0 L`;
- biblioteca exibindo `120+` exercícios;
- favoritos exibido como `0`;
- categorias de exercícios renderizadas como cards estáticos;
- várias ações de CTA sem persistência.

**Recomendação:** toda métrica deve vir de store/API ou ser rotulada como demonstração. Para dados vazios, usar estados vazios úteis com CTA real, não números fixos.

#### 7. O wizard web não cobre a diferenciação completa de coach e aluno

O wizard web coleta sexo, idade, peso, altura, atividade e objetivo, mas o fluxo de coach precisa incluir explicitamente:

- tipo de conta;
- CREF/registro profissional;
- objetivo profissional;
- plano escolhido;
- convite do primeiro aluno ou criação de carteira.

A versão nativa contém mais campos relacionados a coach que a camada web ainda não expõe.

#### 8. Navegação deve evoluir de “voltar” para hierarquia de informação

O botão de retorno universal foi adicionado, o que é correto. O próximo passo é complementar com:

- breadcrumb em telas de detalhe;
- título contextual (“Treino / Push A”);
- estado ativo da sidebar por pathname normalizado;
- preservação do scroll/filtros ao voltar;
- atalho de teclado `Alt + seta esquerda` ou comportamento equivalente;
- suporte a `prefers-reduced-motion` para as transições.

## Backend e infraestrutura

### 9. Há três superfícies de backend que precisam ser racionalizadas

O repositório contém:

1. Supabase como fonte de dados, auth, RLS, RPCs e billing;
2. `server/` com Express/tRPC/Drizzle e um scaffold ainda pouco utilizado;
3. `ai-api/` como serviço FastAPI separado.

O app principal chama diretamente o Supabase em `src/api/supabase.ts`. O `server/` não aparece como backend principal dos fluxos de produto, enquanto a AI API é usada de forma independente.

**Recomendação arquitetural:**

- manter Supabase como backend transacional principal no curto prazo;
- tratar `server/` como camada BFF apenas se houver necessidade real de segredos, agregações ou webhooks;
- documentar e remover o scaffold não usado, ou migrar conscientemente os endpoints para ele;
- manter a AI API isolada, mas com contrato versionado e deployment próprio.

O maior risco atual é alguém assumir que o Express/tRPC é o backend principal, quando a aplicação efetivamente depende do Supabase.

### 10. AI API precisa de endurecimento de produção

Pontos identificados em `ai-api/main.py`:

- não há middleware de CORS explícito;
- há fallback por `X-User-Id`/body quando `ALLOW_INSECURE_USER_ID=true`, que deve ser impossível em produção;
- rate limit local é memória de processo quando Upstash não está configurado;
- cache de análise é memória de processo;
- feedback é salvo em JSONL local, inadequado para ambiente serverless ou múltiplas réplicas;
- o chat aceita histórico, mas precisa de limites explícitos de tamanho para custo e abuso;
- `/health` informa apenas que o processo subiu, não que dependências críticas estão disponíveis.

**Recomendação:**

- CORS com allowlist dos domínios Vercel/prod e sem origem refletida genericamente;
- exigir JWT Supabase em produção;
- Upstash obrigatório fora de desenvolvimento;
- persistir feedback em tabela Supabase ou banco próprio;
- limitar tamanho de mensagens, contexto e número de mensagens;
- adicionar request ID, logs estruturados e métricas de latência/custo;
- health/readiness separado para Supabase, Redis e provedor LLM;
- testes de contrato para `/analyze`, `/chat`, `/usage` e `/feedback`.

### 11. RPCs `security definer` precisam de checklist de segurança

As migrations B2B usam diversas funções `security definer`, o que é uma boa escolha para operações controladas, mas deve haver uma revisão específica para:

- `set search_path` fixo nas funções;
- validação de `auth.uid()` em todas as entradas;
- impossibilidade de alterar `coach_id`/`client_id` indevidamente;
- idempotência de convites, prescrição e webhooks;
- limites de tamanho de payload JSON;
- autorização de leitura por tenant.

As políticas RLS existem e são um bom ponto de partida. O próximo passo é adicionar testes SQL de isolamento entre dois coaches e dois alunos.

### 12. Billing está preparado no banco, mas precisa de testes de integração

Há migrations e Edge Functions de Stripe, porém o fluxo completo precisa ser validado em ambiente de teste:

- checkout iniciado pelo web;
- webhook assinado;
- evento duplicado;
- cancelamento;
- falha de pagamento;
- troca de plano;
- expiração de trial;
- atualização de `coach_plan` e limites de convites.

Nenhum desses casos é coberto pela suíte unitária atual.

### 13. Corrigir a configuração do pnpm

O comando apresenta o aviso de que o campo `pnpm` em `package.json` não é mais lido pelo pnpm 9.12.0 e que `pnpm.overrides` foi ignorado.

**Recomendação:** mover overrides/configuração para `pnpm-workspace.yaml` conforme a versão adotada, ou fixar explicitamente a versão do pnpm no CI. Isso evita que desenvolvimento e CI resolvam dependências diferentes.

### 14. Termos legais ainda têm placeholders de lançamento

`src/legal/legalTexts.ts` contém `[PREENCHER: Cidade/UF]`, e a documentação comercial ainda marca controlador, contato LGPD, canal de solicitações e foro como pendentes.

Isso deve ser resolvido antes de cobrança real e distribuição pública, junto com política de retenção/exclusão e fluxo de exportação de dados.

## Minha recomendação de próximo trabalho

Eu priorizaria agora um **Sprint Coach Web de ponta a ponta**, em vez de continuar adicionando telas isoladas:

1. `WebClientWorkspaceScreen`;
2. prescrição de treino funcional;
3. plano de nutrição funcional;
4. medidas e check-ins;
5. conexão dos atalhos do dashboard;
6. testes com dados de dois coaches e dois alunos;
7. preview com um fluxo completo: convidar aluno → aluno aceita → coach prescreve → aluno executa → coach vê check-in.

Esse fluxo valida simultaneamente frontend, RLS, RPCs, navegação, estados de loading/erro e proposta B2B. Depois dele, a evolução do restante do produto fica muito mais segura.
