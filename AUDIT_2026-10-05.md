# Estado atual e plano de evolução do VRTX — 05/10/2026

## Resumo executivo

O VRTX está em uma fase de **expansão web sobre uma base mobile funcional**, com o principal ciclo de Coach Web já implementado na branch `feat/web-redesign-v2`.

A branch atual está sincronizada com o remoto e sem alterações locais pendentes. O Pull Request #3 continua aberto, está marcado como `MERGEABLE`, e os checks de lint, typecheck, unit e Vercel estão verdes.

O produto já tem uma base relevante para:

- autenticação Supabase;
- onboarding web e mobile;
- treino, dieta, histórico e progresso;
- Coach IA;
- premium e billing;
- coach/aluno;
- prescrição de treino;
- aderência;
- medidas corporais;
- plano nutricional;
- RLS, RPCs e migrations B2B;
- Edge Functions de Stripe, RevenueCat e exclusão de conta.

O principal desafio atual não é falta de telas. É **fechar os fluxos**, reduzir divergência entre mobile e web e transformar superfícies visualmente prontas em funcionalidades totalmente conectadas.

### Avisos importantes

O projeto mostra repetidamente:

```text
The "pnpm" field in package.json is no longer read by pnpm.
```

O override atual está em `package.json` dentro de `pnpm.overrides`, mas a versão adotada do pnpm informa que essa configuração deve ser migrada para o formato suportado pelo workspace. Isso pode gerar diferenças entre instalação local e CI.

Também existe uma configuração duplicada entre `app.json` e `app.config.ts`. O Expo efetivamente resolve o projeto pela configuração dinâmica, mas manter as duas fontes divergentes aumenta o risco de:

- ícones diferentes entre build e desenvolvimento;
- permissões divergentes;
- plugins divergentes;
- comportamento inconsistente entre EAS, Metro e CI.

### Pendências funcionais mais relevantes

#### Coach IA web

`WebSectionScreen` ainda possui o CTA “Gerar leitura” sem ação real:

```tsx

```

A integração existe em `src/services/AIInsights.ts` e na tela mobile, então o próximo passo deve ser extrair o fluxo para uma tela web própria com:

#### Premium web

A tela de assinatura ainda usa `Alert.alert` para os planos. O banco e as Edge Functions de Stripe existem, mas o web ainda não inicia o checkout real.

O fluxo precisa incluir:

- escolha de plano;
- chamada de `createCoachCheckoutSession`;
- loading;
- tratamento de falha;
- redirecionamento para checkout;
- retorno de sucesso/cancelamento;
- atualização do plano atual;
- estado de assinatura pendente ou expirada.

#### Dados estáticos

Ainda existem informações demonstrativas na camada web, por exemplo:

- água exibida como `0,0 L`;
- biblioteca com `120+` exercícios;
- favoritos sempre `0`;
- categorias estáticas;
- gráfico de progresso com alturas fixas;
- alguns CTA sem persistência.

Em produção, cada número deve vir de store/API ou ser explicitamente tratado como estado vazio/demonstração.

#### Builder de treino

O construtor web já permite exercícios, séries, carga e repetições, mas ainda precisa distinguir claramente:

1. começar agora;
2. salvar treino avulso;
3. salvar como template;
4. prescrever para aluno;
5. duplicar treino anterior.

Hoje a experiência ainda mistura criação e início de sessão. Esse é um ponto importante para aproximar o web de Hevy e de ferramentas maduras de treino.

#### 1. Fluxo de treino durante execução

- retry com backoff;
- resolução de conflito;
- identificação de item pendente;
- logs seguros para diagnóstico;
- teste com perda de rede durante treino.

#### 3. Nutrição

- melhorar edição de refeições planejadas;
- escanear ou sugerir alimentos com feedback claro;
- permitir duplicar refeição;
- salvar refeições favoritas;
- sincronizar água com o resumo diário;

#### 4. Onboarding

O mobile coleta mais contexto que o web, mas ainda deve ter:

- validação de campos mais clara;
- unidades explícitas;
- resumo antes da confirmação;
- possibilidade de editar dados sem reiniciar tudo;
- distinção mais clara entre atleta e coach.

- alerta de inatividade;
- prescrição por template;
- histórico de alterações;
- confirmação antes de arquivar;
- ações em lote quando a carteira crescer.

## 5. Backend e segurança

### Supabase

O Supabase é, na prática, o backend transacional principal do produto:

- auth;
- dados de usuário;
- RLS;
- RPCs;
- coach/aluno;
- prescrições;
- check-ins;
- medidas;
- nutrição;
- billing.

As migrations B2B já existem e as tabelas principais têm RLS. Isso é uma boa fundação.

### Riscos a corrigir antes de produção ampla

#### RPCs `security definer`

As funções devem passar por uma revisão sistemática para garantir:

- `set search_path` fixo;
- validação de `auth.uid()`;
- impossibilidade de trocar coach/aluno indevidamente;
- limites de payload JSON;
- idempotência;
- autorização por tenant;
- testes entre dois coaches e dois alunos.

#### AI API

A AI API está separada em FastAPI, mas ainda precisa de endurecimento:

- CORS com allowlist real;
- JWT Supabase obrigatório em produção;
- `ALLOW_INSECURE_USER_ID=false` garantido fora de desenvolvimento;
- Redis/Upstash obrigatório para múltiplas instâncias;
- persistência de feedback fora de JSONL local;
- limite de tamanho do histórico de chat;
- limites de custo e tokens;
- request ID;
- logs estruturados;
- health/readiness separado;
- testes de contrato dos endpoints.

O endpoint `/health` atualmente confirma principalmente que o processo subiu; ele não verifica a disponibilidade das dependências críticas.

#### Billing

A fundação de Stripe existe, incluindo:

- checkout;
- webhook assinado;
- registro de eventos;
- idempotência por `provider_event_id`;
- atualização de plano do coach.

Ainda faltam testes de integração para:

- checkout concluído;
- evento duplicado;
- renovação;
- cancelamento;
- falha de pagamento;
- reembolso;
- troca de plano;
- expiração;
- atualização dos limites de convite.

#### Backend duplicado

O repositório contém três superfícies:

1. Supabase;
2. `server/` Express/tRPC/Drizzle;
3. `ai-api/` FastAPI.

O app principal usa diretamente o Supabase. O `server/` parece mais scaffold ou camada potencial de BFF que ainda não é o caminho principal do produto.

Recomendação: documentar explicitamente essa decisão e evitar que novas regras sejam espalhadas entre três backends sem necessidade.

## 6. Qualidade, CI e testes

### Atual

A CI tem workflows separados para:

- lint;
- typecheck;
- unit;
- E2E manual.

Os testes unitários estão verdes, porém ainda não existe uma barreira E2E real no merge.

### Problema do E2E atual

Os arquivos Detox ainda contêm sinais de scaffold antigo:

- descrição `IronLog Main Flow`;
- expectativa de `Bem-vindo ao IronLog`;
- teste starter com `welcome`, `hello_button` e `world_button`;
- fluxo não alinhado com as rotas web e mobile atuais.

Esse E2E não deve ser tratado como proteção real do VRTX até ser reescrito.

### Plano de testes recomendado

#### Smoke web

- onboarding;
- login;
- forgot password;
- reset password;
- home;
- treino;
- criação de treino;
- histórico;
- Coach Dashboard;
- workspace do aluno;
- prescrição;
- nutrição;
- aderência;
- medidas.

#### Fluxo B2B completo

1. coach cria convite;
2. aluno aceita convite;
3. coach vê o aluno;
4. coach prescreve treino;
5. aluno executa treino;
6. aluno envia check-in;
7. coach vê aderência;
8. coach cria plano nutricional;
9. aluno registra refeição;
10. coach vê aderência nutricional.

#### Isolamento

- coach A não visualiza aluno de coach B;
- aluno A não visualiza plano de aluno B;
- arquivamento não afeta outro coach;
- RPCs recusam `client_id` não autorizado.

## 8. Minha recomendação objetiva

O próximo trabalho não deveria ser apenas outra tela visual. Eu priorizaria o seguinte fluxo de alto valor:

> **Coach IA web real + Premium/checkout real + smoke E2E do fluxo Coach → Aluno.**

Esse pacote fecha três lacunas de produto simultaneamente:

- transforma um CTA visual em funcionalidade real;
- valida monetização;
- cria proteção contra regressões no fluxo B2B que agora é o diferencial do VRTX.

Depois disso, a prioridade deve ser a paridade de dieta, templates e histórico entre mobile e web.
